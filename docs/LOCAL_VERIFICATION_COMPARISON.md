# 原装 Grok 接入本地验证工具：比较结果

CSV a3 是负结果；最新服务产品 a5 相对历史 native a4 多用 0.31% 会话 usage，未实现净降本。较早的隔离服务 a4 单对少用 7.58% usage，但不能代表后续实现，也未证明混合任务普遍或大幅降本。服务验证能力已通过业务和范围检查，性能结论仍有限。最终交付同时包含正常分发的脱敏指引；有效性按完整任务结果判断。

本次问题是：原装 Grok 只接入完整产品，是否能在保留交付质量的条件下降本增效。双方使用 Grok CLI 1.0.41、Grok 4.7/high、同一固定任务与合成输入、全量 native 能力、新任务目录与隔离客户端环境；没有私人规则或 benchmark 专用 guide。产品组额外接入完整 MCP，并接收正常分发的脱敏初始化指导。完成比较使用进程内 auto 权限模式，仍保留分类、拒绝和询问机制，没有修改全局账号、规则或权限。没有模型轮次或整体任务时长截断。

比较的是完整产品，包括工具发现与正常指导，不能把差异单独归因于 `rw_verify` 函数。a1/a2 源码为 `e181de2706a9dea846a2456bbe2128b5488d1577`，a3/a4 为 `2a653ec0d602f5b1834802c3af8dc3d6f1964449`，服务产品 a5 为 `843a3d75bb54741012224c436b7c10e19aecef9f`。它们不是同一实现的重复样本。

CSV a3 产品组比 native 多用 **24.73% 会话 usage、5.13% 外部时间**；按节省率表示为 **−24.73%、−5.13%**。质量相同，但这个样本是效率负结果。它按产品→native 串行执行，未随机化，也不能统一操作系统与服务端缓存状态；不能推出所有 CSV 任务都会变慢。

产品组自然发现工具，并通过普通文件桥调用一次 `rw_verify`，25/25 提交断言及两次显式执行通过，工具阶段耗时 0.422 秒，没有参数错误。但模型生成了 9,972 字符的 JSON 断言清单；native 生成 9,633 字符的 Python 检查器并作 95 字符修正。应用代码也分别为 11,006 与 8,423 字符。这里观察到验证表示被替换为相近大小的清单，未省掉整个生成阶段。两组自行编写的检查合同并不完全相同，不能把每段生成都归为浪费或单独计算工具的因果贡献。

CSV a2 的 16 个响应、18 次工具调用与全部 895,136 usage 保留。四次 `rw_verify` 调用中，三次因分组计数/筛后行数混淆或不支持的 `column` 字段失败，一次通过。模型在第一次工具错误前已经写好并通过 native 检查器，因此不能说它是接口错误导致的回退。后续命名与错误信息修订解决了具体接口歧义；a3 无协议错误仍没有端到端节省，不能用接口修复冒充性能成功。

服务 a3 产品组确实通过一个阶段完成了 21 次真实 HTTP 请求、一次重启、两次启动与清理；自有服务全部停止。但 native 在生成过程中读到独立 oracle，并读取另一组 README。该组 18/18 是完成后重新执行的业务断言结果，不能恢复生成过程的隔离性。双方成本全部保留，**这一对不作为比较收益证据，不展示其表面差值为节省**。工具调用通过也不能替代完整独立业务验收。

隔离服务 a4 双方业务断言均为 18/18。产品组少用 54,314 observable usage（7.58%），外部时间少 225.156 秒（23.44%）。产品一次 `rw_verify` 耗时 2.266 秒，完成 46 次 HTTP 请求和一次重启；`execution_count=51` 是执行事件数，包括请求、启动、就绪和重启，**不是 51 个进程**。产品组另用原生工具验证坏 JSON/UTF-8，遇到 `$pid` 只读变量错误；这些验证与恢复成本全部计入。native 自写检查器错误拒绝标准库 `__future__` 导入（trace 11），模型修改源码后重跑，这项失败成本也保留；三个自有服务进程最终清理，没有删除或杀掉无关服务。

从生成量看，native 自写验证器为 14,096 字符，产品 HTTP 清单为 6,478 字符；产品仍补写了 3,266 字符的原生请求辅助代码，因为受测接口不能表达坏 JSON 原始字节和非法 UTF-8。该辅助代码响应及后续进程检查响应合计含缓存 usage 为 134,371，但它们也包含上下文和必要检查，**不能将此合计当作接口修复后的预测节省**。这里支持批量执行生命周期检查的具体价值，也暴露了漏掉原始请求边界会引回第二套验证代码的缺口。

时间差需要谨慎解释：native 从 trace 5 工具结束到第三个响应（trace 6），即 `06:49:37.354742Z` 至 `07:02:12.098857Z`，有 **754.750 秒未归因运行时/提供方间隔**。这不是已识别的推理或工具执行时间，也不能扣除后伪造一个替代成绩。保留原始墙钟成本，同时不把此次时间优势外推为稳定吞吐收益。native 为 10 个响应、12 次工具调用，产品为 11 个响应、12 次工具调用；少轮次不是这里的节省机制。

## 成本与范围口径

本次 `rw_verify` 开发阶段九次 Grok 会话合计 **6,787,575 observable usage、5,912.187 外部秒数**。此前六次仍保留为 4,689,294 usage、3,384.358 秒，a4 增加 1,379,288 usage、1,696.126 秒，产品 a5 增加 718,993 usage、831.703 秒。历史 native a4 只计一次。合计包含设置阻断、接口返工和受污染样本，不静默剔除。它不是整个项目或所有模型的总成本，旧 DSH 批次与旧 Grok 规则试次由既有报告单独保留。

usage 是客户端报告的 input、output、cache-read、cache-creation 字段之和，含缓存，不是账单或金钱成本。auto 安全分类器消耗未单独暴露，不能声称已完整计入。API 秒数是客户端汇总，不是纯推理时间；外部时间覆盖该 arm 的 CLI 运行，包含启动、工具及权限等待。主控 Codex、开发、独立验收和未暴露消耗不在这个九次会话合计中。逐项数字与判定见 [结果 JSON](../benchmarks/results/2026-09-30-local-verification.json)。

业务、范围、清理和比较有效性分开记录。CSV 任务没有一律禁止目录外辅助写入；两组都曾写系统临时验证材料，native 删除了自己的检查器，产品组未请求删除。a2 对自有辅助检查器和任务内验证证据的删除被拒绝，未绕过拒绝。服务产品 a3 的业务数据库和证据留在任务目录，常规客户端日志与缓存按任务例外单列。PowerShell `$PID` 只读变量造成的一次清理检查错误保留，随后检查确认自有服务进程已退出；不据此声称系统受损或数据泄漏。

## 隔离、说明一致性与复现材料

a4 使用新的隔离服务配对。双方运行前后候选全树干净、源码身份保持一致；读取审计没有发现 oracle、另一组产物或子代理的外部业务读取，自有服务均停止。native README 声称拒绝 `0.0.0.0` 时退出码为 2，实际源码为 1；合同未规定具体退出码，业务 18/18 仍成立，但说明与实现不一致单列保留。产品说明与实现一致。旧受污染 a3 继续保留，不以新结果替换或删除其成本。

以下固定材料已放入 `benchmarks/local-verification/` 并经过隐私审查：

- `csv-task.txt`：固定 CSV 业务合同。
- `csv-input.csv`：398 字节合成中文 CSV，包含重复、冲突、负数和格式异常。
- `verify_csv.py`：独立 15 项验收与重复运行检查。
- `service-task.txt`：标准库 SQLite/HTTP 合同、重启持久化及错误请求要求。
- `service-task-isolated.txt`：a4 准确的隔离版本任务，不能替换 a3 原始合同。
- `verify_service.py`：独立 18 项服务验收。

固定任务/输入按实际受测版本分别保存。oracle 可公开供复现，但生成中的模型任务必须与它及另一组产物隔离；验收可见性是此次已经出现的真实风险，不能只靠任务提示解决。具体操作见复现材料中的 README。

公开材料只含合成输入、固定合同、独立断言、脱敏摘要及可定位 trace 行号。不复制私有 runner、配置、认证引用、客户端 home、运行目录、账号/设备信息、原始 trace 或完整模型清单。

## 最新服务候选与未测修订

服务产品 a5 在新冻结候选 `843a3d75bb54741012224c436b7c10e19aecef9f` 上独立通过 18/18 业务断言。源码运行前后全树干净、身份一致，范围、loopback 限制、README 一致性及自有进程清理均通过审计。提示与 a4 同字节，但 native 沿用历史 a4；产品能力和正常分发指导同时改变，且执行时间与缓存不受控。这是新完整产品的单次观察，不能单独归因于 `body_base64` 字段，也不是新增的配对重复。

该次用量为 152,369 input、54,624 output、512,000 cache-read，合计 **718,993**；外部 831.703 秒，客户端 API 汇总 757.115 秒，12 个响应、13 次工具调用。相对历史 native a4，多 2,192 usage（**+0.31%**）；相对产品 a4，多 56,506（**+8.53%**）。外部时间比 native 少 128.938 秒（13.42%），但复用 native 的 754.750 秒未归因间隔，仍不能推出稳定时间收益。

模型自然发现并使用 `body_base64`，17 个原始字节请求进入同一次 `rw_verify`。该阶段 2.140 秒完成 38 次 HTTP 请求、一次重启、两次启动和两次清理，43 是混合执行事件数。旧的独立 HTTP 辅助代码与第三个服务确实消失；但准备 Base64 的 947 字符 `python -c` 命令出现引号 `SyntaxError`（响应 7，trace 14/15），随后用 1,298 字符 heredoc 恢复（响应 8，trace 16）。两个准备命令均尚未启动服务，失败和恢复成本全部保留。

没有完整工具 result 或本地日志回流，不能把额外成本归因于 `checks_total=0`；这个字段只数文件断言，HTTP 结果由整体 `passed`、首个失败与执行证据表示。相对 a4，a5 累计 input+cache-read 增加 49,781，output 增加 6,725；这说明少掉一个辅助服务并未自动减少整个会话负担，但不能仅凭缓存分布或字符数判定提供方机制、推理量或预测节省。

最终接口同时支持 `body_text` / `body_bytes` 原样输入。实际 `agent.py` JSON CLI 一次回放通过：将 a5 的 17 个 Base64 请求改为 16 个 text、1 个 bytes，39 步的原始请求字节、其他字段、断言和顺序保持一致。使用 a5 已验收源码的独立副本和开始时不存在的新数据库，原模型产物不变；38 次 HTTP 请求、一次重启、两次启动和两次清理均通过，43 个执行事件，工具阶段 2.078 秒、CLI 2.250 秒。归一化声明从 6,127 到 6,049 字符，**这仅证明 API 可省去编码准备，不当作 token 收益；最终修订没有端到端模型性能测量**。没有再次运行模型或独立业务 oracle。不以 a4 的 7.58% 当作最终版本成功，也不从移除编码错误推算一个未发生的模型成绩。上述模型比较与回放期间未修改个人规则、未安装用户级 MCP。

最终原样请求 API 的开发提交为 `81edc870915db6bcabde5d52baeec3d0cb4fc3ea`，公开源码提交为 `dadc5c15562671fc0746ff2b4a0fd1061914190d`；这两个身份对应最后功能修订，不能与受测 a4/a5 候选混写。
