# 为什么这轮DSH工具收益弱，历史Grok较好

2026-09-30。[机制数据](../benchmarks/results/2026-09-30-mechanisms.json) · [DSH 全部重复结果](DSH_REPEATED_COMPARISON.md) · [Grok 日常规则对照](GROK_DAILY_EFFICIENCY.md)。

已完成证据复审，不新增模型基准。DSH业务16/16通过；保守范围审计11/16，包含2项课程明确越界与3项Bottle/Flaskr解释性范围问题。全部成本保留，不能把含偏离的合并变化叫完全合规收益。新旧Grok日常规则负对照由其独立报告负责。

**少轮次并不保证少token。** 两次DSH重复合计：

| 任务 | 工具/原生响应 | 平均input/响应 | output合计 | total合计 |
| --- | ---: | ---: | ---: | ---: |
| Bottle | 20/46 | 17692.0/19529.2 | 31048/42765 | 384888/941107 |
| 静态站 | 31/40 | 17924.5/12746.4 | 27041/23256 | 582699/533113 |
| Flaskr | 30/47 | 25965.0/17861.9 | 43624/36480 | 822573/875991 |

input包括uncached与cache reads的累计处理量，不是唯一上下文或价格。Bottle响应、平均输入和输出同向下降；静态站虽少22.5%响应，平均输入却多40.6%，输出也多，total最终多9.30%。Flaskr也有更重上下文与输出，不能仅用轮次数解释收益。

**宿主的固定税不同。** DSH四任务各两次重复，工具首次input+cacheRead都恰比原生多3218 token；request/header第14行、seq10显示20项工具定义/22694序列化字符，原生11项/11450字符。3218是组别初始上下文差，含schema、指南和模式，不能全归schema。

旧Grok首响应组别差约263–275 token。init列表没有rw名称，模型先search_tool再调用rw_run：Bottle工具trace第2/3行发现5项；Flaskr第2/3行limit=1只返回rw_run；静态站第2/3行先5项、第4/5行再3项。支持初始化/按需发现路径不同，但旧trace缺逐轮provider tools定义，不能证明每轮只注入rw_run或算出精确schema税。发现结果本身仍占对话。

**最差静态站有一个具体慢步骤。** 第一工具对比原生，多47.891秒；可识别工具阶段多42.001秒，模型响应阶段仅多5.578秒。四个含Test-NetConnection的就绪/停服检查耗时41.589秒：seq79/89/101/111，trace行83/93/105/115，分别8.253/9.540/7.681/16.115秒。第二工具轮不用它，仍25/25通过，全部工具阶段15.392秒。复合命令还含HTTP/Git，不能把41.589全归该cmdlet。

授权后的无模型、无外网判别检查只启动自己的临时127.0.0.1 HTTP服务，结果如下，八项判断正确且服务已停：

| 状态 | 原模式 | 短HTTP已知正文 | 500ms TCP | 拥有PID判断 |
| --- | ---: | ---: | ---: | ---: |
| 就绪 | 7.296秒 | 0.036秒 | 0.006秒 | 0.011秒 |
| 已关闭 | 8.287秒 | 1.067秒 | 0.515秒 | 0.013秒 |

原模式显式sleep均0，命令模式本身有可避免等待。仅一次每状态、顺序非随机且含模块加载，不能外推完整任务收益。HTTP用于就绪业务正文，socket/PID用于关闭，不替代真实业务及重启验收。

**历史Grok的原生路线更重，所以更容易抵消工具税。** Bottle响应20/40、调用34/57、read_file9/24；静态站22/24、39/44、13/19；Flaskr31/27、50/53、16/24。Bottle原生读bottle.py12次、工具7次，各仅一对范围重叠，多数是不同范围，不能称为重复读同一段。更多源码/API探索、产物检查与回合会扩大累计历史。旧Grok API/wall约89.86%–97.01%，但无事件时标，不能把该数字精确解释为纯思考或拆出安装/网络耗时。

两个反例阻止泛化：旧Grok Flaskr工具响应反而更多、token几乎不变；新DSH严格可比静态站两对合并时间多26.37%、token多9.30%。课程与静态站的两次DSH结果方向也反转。旧Grok课程还含40轮中断及4轮续接，不能称严格无干扰效果。

**工具真正做了获取/环境批处理，本批次没有证明服务恢复省钱。** 所有工具尝试仅一次rw_run安装准备，任务文件由原生工具写；没有实际rw_replan/status/cancel调用。恢复接口有生命周期价值，不能因本轮未用而删，也不能据此声称恢复成本收益。Flaskr第一工具组11响应但12次read，原生24响应却10次read，说明文件批处理和模型策略同样影响轮数。领域校验脚本、额外验收与目录偏离可吃掉节省。

改进优先考虑总token，其次才是耗时，并尽量同时下降。已有环境直接native；遵循返回的准确cwd和解释器，减少失败回合；不重新获取明确仓库、不读完整成功日志；针对尚不确定的API读相关范围，批量处理独立文件工作；给主动临时验证数据明确的任务scratch目录。宿主支持时可懒加载MCP且保留恢复能力，但未做schema消融，单纯缩字不能宣称整个任务更省。短HTTP/套接字/PID探测的本地证据主要是时间收益，尚未证明token收益。质量、业务拒绝、重启/持久化与范围约束都不削减。

为判断是否能直接开启按需加载，另只读检查了本机该版 SDK：`@deepseek-ai/dsh-mcp-client/lib/index.js` 的 `syncTools` 先获取完整分页再注册全部工具，公开配置 schema 没有工具按需发现开关；`dsh-agent-tool-presentation` 只列 native/ptc/both。这个检查范围内未找到可直接启用的等价开关，因此没有修改宿主或将 programmatic tool calling 冒充懒加载。它不证明其他版本或插件不能实现；更换呈现方式需要单独核对完整能力、实际上下文和任务结果。

紧凑数字与定位引用见[机制数据](../benchmarks/results/2026-09-30-mechanisms.json)，局部判别结果见[八项状态检查](../benchmarks/results/2026-09-30-local-probe.json)。原始逐调用记录留本地，不公开。实际requested reasoning未覆盖，旧、新DSH effective均high；同名high不证明跨供应商等计算强度。

如需复现局部探测，将 [Python 入口](../benchmarks/check_local_probe.py) 和 [PowerShell 检查](../benchmarks/check_local_probe.ps1) 一起复制到新的空目录，用已有 Python 运行 `python check_local_probe.py`，另需已有 `pwsh`。脚本只创建和停止自己的 loopback 服务，在该目录写入 `local-probe-verification.json`，不调用模型、不访问外网、不安装依赖。使用新目录保留每次结果，不覆盖历史证据。
