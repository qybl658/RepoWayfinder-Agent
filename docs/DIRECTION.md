# 方向与取舍

## 这一版解决什么

服务对象是调用工具的 Agent。用户通过 Agent 提交结果目标，本工具负责确定性的仓库执行与证据，不再多套一层模型规划。小白可以是最终受益人，但不再让这个分支承担菜单、账户配置向导和通用桌面交互。

主要价值假设：把反复出现的获取源码、虚拟环境、运行、日志筛选、结果断言和恢复收敛成少量工具调用，让模型把上下文留给任务判断。相比 Agent 原生终端，是否更快、更省或更可靠，必须由同目标实测决定。

## 当前边界

- 从 MCP/JSON 接入 Windows 本地执行；公开 GitHub 仓库、固定提交、有限时长任务。
- 计划由调用方明确给出；继承启发式只作辅助，不能把安装路线当作用户目标。
- 当前核心仍在 `main.py`，通过每个作业独立进程隔开全局状态。暂不为架构整洁重写全部执行代码。
- 支持 pyproject 声明的 CLI，限定使用该作业虚拟环境；日志、完整产物不默认进入模型上下文。
- 不承诺容器隔离、任意仓库成功、长期服务托管、通用代码编辑或任意系统自动安装。

## 后续按证据推进

1. **先证明重复收益。** 在用户真实需要的 CLI、数据转换、小型项目运行中继续成对比较。记录失败，使用相同模型、提交和目标；交替顺序，区分缓存、网络和模型变化。持续没有收益的场景交还 Agent 原生终端。
2. **再做可复用任务。** 仅把已经通过结果检查的计划升级为可复用配方，绑定源码版本、依赖与检查；失效时返回明确原因。重复任务才考虑缓存和增量执行，避免让旧输出冒充新结果。
3. **需求证明后才扩执行边界。** 多 Agent 并行、持久服务、容器或远程执行分别需要真实需求与独立验收。到那时把确实要共享的执行功能从旧核心抽离；不用兼容旧菜单约束新接口。

停止或转向条件：若维护项目配方的成本持续超过节约的调度和排错成本，收缩到日志与结果验证；若成熟 Agent 的原生能力稳定达到同等效果，不继续靠包装命令维持独立平台。

单次漂亮结果只支持继续试用。首次失败、修复成本和开发过程消耗也应保留，不能只宣传修好后的数字。

## 2026-09-27：从补命令转向完整任务周期

两轮 DSH 试验暴露的共同原因，是把首次执行做成批处理，却把失败恢复留给模型重新组织。多包装一层 shell 本身不构成收益；强迫模型生成大脚本还会放大输出与推理开销。本轮没有重写全部旧执行核心，调整的是 Agent 层的任务协议：

- **作业负责环境。** checkout、固定源码提交、虚拟环境跟随 job，任务修订不重新获取或安装。通用可执行程序走统一解析，不按工具名逐个补白名单。
- **修订负责输入。** 新文件与精确替换先整批校验，再记录修订前内容；可只跑受影响命令。配置和文档直接提交，脚本只做必要编排。输入事务中断能恢复，外部修改发生冲突时保留现场；命令及依赖副作用不能自动回滚。
- **尝试负责执行和结果。** 启动锁、一次性认领令牌和实际 worker PID 负责单个活动执行。自动执行不暴露手动 prepared 中间态；新尝试清除旧摘要，报告按尝试单独保存。重复 request_id 查询已提交操作。失败摘要列出已成功命令和失败命令，方便选择重跑范围。
- **验收负责真实用途。** 文件新鲜度只是大小/时间变化信号，不能证明内容来源或完整目标。成对试验另查真实内容、链接、归档和搜索索引效果；不把搜索系统正常词干化判作失败。

这解决的是一类重做与状态归属问题，尚不能证明普遍省 token。后续只在真实试验支持时扩展可复用任务配方；若通用复杂生成仍比原生工具贵，就明确收缩适用范围，不靠增加提示与特例追逐每个任务。
